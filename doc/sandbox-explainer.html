srt confines a command with operating-system rules; twsrt builds those rules from fragments

A coding agent runs shell commands as you. srt (Anthropic sandbox-runtime) runs such a command under the macOS or Linux sandbox, with a file policy and a network allowlist. twsrt compiles the policy from commented .jsonc fragments, so the Cobra team standard and individual additions stay separate and reviewable.

paths relative to the repo root
edittools/sandbox/srt/twsrt/srt/*.jsonc
compiletwsrt -c tools/sandbox/srt/twsrt/config.toml generate -w
runsrt -s tools/sandbox/srt/twsrt/srt-settings.json -c "copilot"
The generated srt-settings.json is git-ignored. Edit fragments, not the JSON.

What srt is

A wrapper that starts one command under the OS sandbox: Seatbelt on macOS, bubblewrap on Linux. The command keeps your user, files and toolchain. There is no VM and no image.

What it enforces

Writes are denied unless a path is listed. Reads are allowed unless a path is listed. Network is denied unless the host is on the allowlist; every connection goes through a proxy that srt runs on localhost.

For you

Change a fragment, run twsrt … generate -w, start the agent with srt -s …. The default profile allows 92 domains and 19 write roots.

1A command started by an agent has your file and network access

Leaking a secret takes two steps: read it, then send it. srt places a check on each step.

Without a sandbox, a command run by Copilot, Claude Code or a local MCP server can read every file your user can read, for example ~/.aws/credentials, and connect to any host. Text in a README, an issue or a web page that the agent reads can ask it to do both (prompt injection). srt does not judge the command. It limits what any command in the process tree can reach.

The srt README calls this the dual isolation model: without file isolation a process can read SSH keys; without network isolation it can send whatever it can read. A sandbox that applies only one of the two does not prevent the leak.

srt keeps the command on your machine, with your tools and files, and restricts what it may touch. A VM gives the command a separate machine instead.

Consequence: srt and the command share one kernel and one user account. The protection is exactly the policy: anything the settings file allows, the command can do as you.

3srt generates a kernel profile per command and routes all network traffic through its own proxy

The kernel checks every file access. Network access is closed except for the localhost ports where srt's proxies listen; the proxies apply the domain lists.

The diagram shows macOS. For each command srt writes a Seatbelt profile that starts with (deny default) and adds the allowed operations, then runs the command with /usr/bin/sandbox-exec. The restrictions apply to the whole process tree, so a shell, a Gradle daemon or a sub-agent started by the command is confined too (process tree below).

What a sandboxed command sees in its environment

srt points tools at its proxy with environment variables. Observed in a shell running under srt v0.0.83 on macOS (proxy token replaced):

HTTPS_PROXY=http://<token>@localhost:49374         # also HTTP_PROXY, ALL_PROXY and lower-case forms
JAVA_TOOL_OPTIONS=-javaagent:…srt-proxy-agent.jar  # JVMs ignore *_PROXY; the agent sets proxy properties
SRT_SSH_PROXY_COMMAND=…                            # GIT_SSH_COMMAND uses it: git over SSH via the proxy
SANDBOX_RUNTIME=1                                  # marker that the process runs under srt

The port changes per run example. A process that ignores the variables cannot bypass the proxy: the kernel refuses its direct connection.

Every process started inside the sandbox inherits the profile

sandbox-exec applies the profile to its own process and then replaces itself with bash -c <command>. Every process that the shell forks or execs carries the same profile, and the kernel refuses any attempt to replace or widen it. The tree below is an example example; the rule holds for any command.

Observed in a shell running under srt v0.0.83 on macOS:

Inside the tree confined

  • every process forked or exec'd below sandbox-exec
  • interpreters and daemons: java, python, node
  • detached processes, also after their parent exits

Same file and network rules; signals and process info only within the sandbox.

Outside the tree own rights

  • srt and its proxies
  • processes started before or beside srt
  • daemons reached over an allowed Unix socket or Mach service, e.g. the Docker daemon in the docker profile

A request to such a daemon runs with the daemon's rights. docker.jsonc calls its sockets "equivalent to a sandbox escape".

4The proxy decides on the host name: denylist first, then allowlist

A connection is forwarded only if no deniedDomains entry matches, an allowedDomains entry matches, and the name does not resolve to a local address.

Observed in a sandboxed shell under the Cobra policy:

$ curl -sS -o /dev/null -w '%{http_code}\n' https://github.com
200
$ curl -sS -o /dev/null -w '%{http_code}\n' https://example.com      # not on the allowlist
curl: (56) CONNECT tunnel failed, response 403
$ curl -sS -o /dev/null -w '%{http_code}\n' https://webhook.site     # on the denylist
curl: (56) CONNECT tunnel failed, response 403

The rule behind it

Matches deniedDomains 403

  • webhook.site
  • *.ngrok.io
  • pastebin.com

Checked first. An allowlist wildcard cannot re-open it.

Matches allowedDomains forwarded

  • github.com
  • *.gradle.org
  • pypi.org

Then DNS; addresses on loopback, link-local, cloud metadata or this host's own interfaces are dropped.

Matches neither 403

  • example.com
  • any new host

Default for network: denied.

How a pattern matches

EntryMatchesDoes not match
github.comgithub.com, any portapi.github.com
*.github.comapi.github.com, a.b.github.comgithub.com (the apex)
api.example.com:443that host on port 443 onlythe same host on port 22

That is why the fragments list both github.com and *.github.com. twsrt doctor --info lists wildcards whose apex is missing.

Limit: the Cobra policy sets no tlsTerminate, so the proxy sees host and port only, not the request. An allowed host can receive any data: with github.com allowed, a process can push to any repository (srt README, Security Limitations).

5Reads are open unless denied; writes are closed unless allowed

The two pairs use opposite precedence: allowRead wins over denyRead, denyWrite wins over allowWrite.

Read

default: every path readable→ denyRead hides a path→ allowRead re-opens inside it, wins

Cobra: 22 denyRead entries, no allowRead.

Write

default: nothing writable→ allowWrite opens a root→ denyWrite closes inside it, wins→ built-in denies, always

Cobra: 19 allowWrite roots, 70 denyWrite entries after compile.

How a path entry is read

"filesystem": {
  "denyRead": [
1    "~/.ssh", "~/.aws/credentials", …
  ],
  "allowWrite": [
2    ".", "/tmp", "~/.gradle", …
  ],
  "denyWrite": [
3    ".git/config",
4    "/**/.env", "/**/id_rsa",
5    "**/*.pem", "**/*.key"
  ]
}
  1. denyRead: the command cannot open these paths. ~ is your home directory. twsrt also copies each entry into denyWrite (chapter 8).
  2. . is the directory srt is started in. Started from $HOME, the whole home directory becomes writable.
  3. Relative entry: only .git/config of the start directory. srt's built-in denies cover .git/config in sub-directories.
  4. Starts with /: /**/.env matches a .env anywhere on disk (macOS).
  5. Relative glob: **/*.pem matches only beneath the start directory. Observed: writing /tmp/probe.pem succeeds in a sandboxed shell.

Built-in write denies

srt adds these to every policy, in the start directory and beneath it, even inside allowWrite. They protect files that other programs execute or trust.

6Each key opens a defined part of the sandbox

Sorted by how much they open: keys that keep the default, narrow openings, wide openings, and openings that give a route out of the sandbox.

Closed default kept

  • deniedDomains (20)
  • denyRead (22)
  • enableWeakerNestedSandbox: false
  • allowAppleEvents: unset

Add restrictions or keep srt's default.

Narrow named items

  • allowPty: true
  • allowMachLookup (4)
  • ignoreViolations

Open named services or change reporting only.

Wide many targets

  • allowedDomains (92)
  • allowWrite (19)
  • allowLocalBinding: true
  • enableWeakerNetworkIsolation: true

Each entry is a place data can go to or code can be written to.

Route out escape

  • allowUnixSockets: /private/tmp
  • docker.sock (docker profile)

A socket to a process that runs outside the sandbox lets the command act through it.

7A profile selects fragments; twsrt unions them into one settings file

Fragments are split by audience, so the generic part can be shared while employer and personal additions stay in their own files.

base.jsonc
Generic macOS policy, safe to share. 82 domains, 20 denied, 19 write roots, every scalar switch.
bmw.jsonc
+10 BMW hosts (GHE, LOS services, AWS MCP).
personal.jsonc
Own repos and notes; never shared. Empty lists today.
docker.jsonc
+2 daemon sockets, +3 registry domains.
compile
srt-settings.json

Strict JSON, written next to config.toml. This is the file srt -s reads.

Profiles in config.toml

1default_profile = "default"

[sources.srt.fragments.base]
2path = "srt/base.jsonc"
# … bmw, docker, personal

3[profiles.shared]
srt = ["base"]

4[profiles.default]
extends = ["shared"]
srt = ["bmw", "personal"]

5[profiles.docker]
extends = ["default"]
srt = ["docker"]
  1. default_profile: used when --profile is omitted.
  2. Fragment registry: a name and a .jsonc path, relative to config.toml. No output key is set, so the result goes to srt-settings.json in the same directory.
  3. shared: base only; the policy you can hand to another team.
  4. default: extends resolves the parent first, then adds this profile's fragments.
  5. docker: everything in default plus the Docker sockets (chapter 6).

8Fragments can only add: lists are unioned, conflicting values stop the compile

twsrt fails rather than let one fragment change a value another fragment set.

1

Resolve the profile

Walk extends depth-first, parents first. A fragment named twice is used once.

config.toml
2

Load and validate each fragment

Strip JSONC comments. The path and domain lists must be lists of strings; enabled must be a boolean.

*.jsonc
3

Reject contradicting lists

A value in allowedDomains of one fragment and deniedDomains of another fails, as does a path in both allowWrite and denyWrite.

can fail
4

Union

Objects merge key by key. Lists gain the items they lack. Equal scalars pass; unequal scalars or different types fail.

can fail
5

Sort

Path lists, domain lists, allowUnixSockets and ignoreViolations are sorted, so the output does not depend on fragment order and diffs stay small.

stable output
6

Add implied write denies

Every denyRead entry, config.toml, each fragment and the output file go into denyWrite. A path in both denyRead and allowWrite fails.

self-protection
7

Write

generate -w writes strict JSON to tools/sandbox/srt/twsrt/srt-settings.json. Every profile writes to this same file.

git-ignored

Step 6 exists because srt turns denyRead into a read deny only: inside a writable root, a file the command cannot read could still be overwritten. In the Cobra profiles the 70 denyWrite entries are 42 from base.jsonc, 22 implied by denyRead and 6 policy files.

The rule by value type

List union

  • allowedDomains
  • denyWrite
  • allowMachLookup

Items from all fragments, without duplicates. A fragment cannot remove an item.

Object recurse

  • network
  • filesystem
  • ignoreViolations

Keys merge one by one; the rule applies again to each value.

Scalar must agree

  • allowPty
  • allowLocalBinding
  • enableWeaker…

The same value in two fragments passes. A different value fails. Set scalars in base.jsonc only.

9Cheat sheet

Commands for daily use, run from the repository root.

State today: the checked-in srt-settings.base.json, used in the README's Operations section, is older than the fragments. Compared with twsrt show -p default it lacks /private/var/run/mDNSResponder in allowUnixSockets and 7 denyWrite entries (~/sandbox.read.test and the 6 policy files). Generate the file instead.

Settings path: srt without -s reads ~/.srt-settings.json. This config.toml writes tools/sandbox/srt/twsrt/srt-settings.json, so pass -s explicitly.

Build and inspect the policy

# compile the default profile → tools/sandbox/srt/twsrt/srt-settings.json
twsrt -c tools/sandbox/srt/twsrt/config.toml generate -w
# compile with Docker access (overwrites the same file; regenerate default afterwards)
twsrt -c tools/sandbox/srt/twsrt/config.toml generate -w --profile docker

# print the compiled JSON without writing
twsrt -c tools/sandbox/srt/twsrt/config.toml show -p default
# list profiles and the fragments they resolve to
twsrt -c tools/sandbox/srt/twsrt/config.toml profiles
# check fragments for conflicts, redundant rules and glob traps
twsrt -c tools/sandbox/srt/twsrt/config.toml doctor --info
# edit fragments or config.toml in $EDITOR
twsrt -c tools/sandbox/srt/twsrt/config.toml edit
twsrt -c tools/sandbox/srt/twsrt/config.toml config

Run and check

# start an agent in the sandbox (from the repo root: "." becomes writable)
srt -s tools/sandbox/srt/twsrt/srt-settings.json -c "copilot"

# is a host allowed? 403 = blocked by the proxy
srt -s tools/sandbox/srt/twsrt/srt-settings.json -c "curl -sS -o /dev/null -w '%{http_code}\n' https://example.com"
# is a file readable? "Operation not permitted" = denied
srt -s tools/sandbox/srt/twsrt/srt-settings.json -c "cat ~/.aws/credentials"

# probe every rule of the effective settings
twsrt -c tools/sandbox/srt/twsrt/config.toml test
# see what was blocked (macOS), or run srt with debug output
log stream --predicate 'process == "sandbox-exec"' --style syslog
srt -d -s tools/sandbox/srt/twsrt/srt-settings.json -c "<command>"
